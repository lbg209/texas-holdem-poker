# 텍사스 홀덤 포커 - 요구사항 정의서

## 1. 프로젝트 개요

- 텍사스 홀덤 규칙을 따르는 포커 게임 백엔드
- Java 17 + Spring Boot 4.1.1 + Gradle
- 백엔드/프론트엔드를 별도 프로젝트로 분리해서 개발 (이 저장소는 백엔드 전용)
- 백엔드 완성 후, 순수 HTML/JS로 만든 최소 테스트 페이지로 먼저 동작을 확인하고
  이후 별도 프론트엔드 프로젝트를 연동한다

## 2. MVP 범위

**포함(In Scope)**
- 단일 고정 테이블 1개 (서버 실행 시 바로 존재)
- 텍사스 홀덤 전체 라운드 진행 (프리플랍 → 플랍 → 턴 → 리버 → 쇼다운)
- 베팅/레이즈/콜/체크/폴드/올인 처리
- 사이드팟 계산
- 족보 판정 및 승자 결정
- WebSocket을 통한 실시간 상태 동기화

**제외(Out of Scope, 이후 단계)**
- 로비, 다중 테이블, 매칭 시스템
- 로그인/인증 (플레이어 ID만으로 임시 식별)
- 실제 결제/현금성 재화
- 토너먼트, 블라인드 인상 구조

## 3. 도메인 구조

com.lbg0146.backend
├── card         # Card, Deck, Suit, Rank — 카드 생성/셔플/딜
├── hand         # HandEvaluator, HandRank — 족보 판정
├── player       # Player, PlayerStatus, PlayerAction
├── room         # Room(게임 상태를 들고 있는 도메인), RoomService(액션 처리 로직),
│                # BettingRound — 진행 중인 게임 상태를 메모리에서 관리한다
├── room.controller  # RoomController(REST) — 방 상태 조회 등
└── websocket    # WebSocket 설정, 메시지 핸들러, 메시지 DTO

- `Room`은 DB에 매번 저장하는 엔티티가 아니라, **서버가 켜져 있는 동안 메모리에서 관리되는 상태 객체**다
  (게임 종료 후 기록만 필요하면 별도로 히스토리 테이블에 저장하는 걸 고려)
- `RoomService`가 액션 하나(베팅/폴드 등)가 들어올 때마다 `Room`의 상태를 어떻게 바꿀지 담당한다

## 4. 게임 기본 값

| 항목 | 값 |
|---|---|
| Small Blind (SB) | (정할 것, 예: 50) |
| Big Blind (BB) | (정할 것, 예: 100) |
| 시작 바이인(칩) | (정할 것, 예: 10,000 = 100BB) |
| 최소 인원 | (정할 것, 예: 2명) |
| 최대 인원 | (정할 것, 예: 6명) |
| 딜러 버튼 | 매 판마다 시계방향으로 한 자리 이동 |

## 5. 액션 순서 규칙

- **프리플랍**: BB 다음 자리(UTG)부터 시작
- **플랍/턴/리버**: 버튼 기준 가장 가까운 활성 플레이어부터 시작 (프리플랍과 시작 위치가 다름에 유의)
- 한 베팅 라운드는 **모든 활성 플레이어가 콜 또는 폴드를 완료했을 때** 종료된다

## 6. 베팅/레이즈 규칙

- 최소 베팅 금액 = BB
- 최소 레이즈 금액 = 현재 베팅액 + 직전 레이즈 폭
    - 예: BB=100에서 A가 300으로 레이즈(레이즈 폭 200) → B의 최소 레이즈는 500 이상
- 예외: 레이즈 최소 단위보다 적은 금액으로 올인한 경우, 이미 액션을 마친 플레이어의 액션은
  다시 열리지 않는다 (그 이후 순번의 플레이어에게만 재액션 기회가 있다)

## 7. 올인 / 사이드팟 규칙

- 칩이 부족한 플레이어가 올인하면, 그 금액까지만 메인팟에 참여한다
- 남은 플레이어들이 그 이상 베팅을 이어가면 별도의 사이드팟이 생성된다
- 올인한 플레이어는 자신이 참여한 팟에서만 승리할 수 있다 (참여하지 않은 사이드팟 제외)
- 여러 명이 서로 다른 금액으로 올인하면 사이드팟이 여러 개 생길 수 있다

## 8. 쇼다운 규칙

- 마지막으로 베팅/레이즈한 플레이어가 먼저 카드를 공개한다
- 전원 체크로 리버까지 진행된 경우, 버튼 기준 가장 먼저 액션한 플레이어부터 공개한다
- 홀카드 2장 + 커뮤니티 카드 5장 중 최적의 5장 조합으로 족보를 판정한다
- 족보 순위(낮음→높음): 하이카드 < 원페어 < 투페어 < 트리플 < 스트레이트 < 플러시 <
  풀하우스 < 포카드 < 스트레이트플러시 < 로열플러시

## 9. 통신 구조

- **REST API**: 방 상태 조회 등 단발성 요청
- **WebSocket**: 게임 진행 중 실시간 상태 동기화 (베팅 액션 수신, 상태 변경/커뮤니티 카드
  공개/쇼다운 결과를 방 전체에 브로드캐스트)
- 같은 방에 대한 액션은 반드시 순서대로(직렬화) 처리한다 — 동시 액션으로 인한 상태 꼬임 방지
- 상세 메시지 스키마는 WebSocket 구현 단계에서 별도 `docs/protocol.md`로 문서화한다

## 10. 빌드 순서

1. 카드/덱 (셔플, 딜) — 순수 로직, 단위 테스트로 검증
2. 족보 판정(HandEvaluator) — 순수 로직, 단위 테스트로 검증
3. Room/Player 도메인 + 라운드 진행 로직 — 통신 계층 없이 순수 로직으로 구현 및 테스트
4. REST로 방 상태 조회 API
5. WebSocket 연결 + 최소 HTML 테스트 페이지 (연결 확인 수준)
6. 실제 게임 액션 메시지 프로토콜 (BET/CALL/RAISE/FOLD) 및 브로드캐스트
7. 방 단위 동시성 처리 (액션 직렬화)
8. 프론트엔드 연동, 이후 로비/멀티룸 등 확장 검토
