# 프론트엔드 요구사항

이 문서는 화면/UX/상태 처리 요구사항만 다룬다. 블라인드·족보·사이드팟·베팅 라운드 규칙 등 게임 자체의 규칙은 `backend/docs/requirements.md`에 있으므로 여기서 반복하지 않는다.

## 0. 구현 범위 구분

| 범위 | 상태 |
|---|---|
| 참가 화면(닉네임 입력, 참가 성공/실패, `playerId` 유지) | **구현 완료 (3단계)** |
| REST 연동 기반 구조(`roomApi`, `RoomContext`, `httpClient`) | **구현 완료 (3단계)** |
| WebSocket 연결/재연결/STATE·ERROR 처리 | 미구현 — 4단계 |
| 포커 테이블 UI(좌석/카드/팟/버튼/턴 표시) | 미구현 — 5단계 |
| 액션 UI(버튼/베팅 금액 입력) | 미구현 — 6단계 |
| 카드 딜링/커뮤니티 카드 등장 애니메이션 | 미구현 — 7단계 |
| 연결 끊김/에러 UX 다듬기 | 미구현 — 8단계 |

아래 항목들은 전부 **요구사항**이며, 이 중 4단계 이후 항목은 아직 설계/구현되지 않았다.

## 1. 참가 화면 (구현 완료)

| 요구사항 | 이유 |
|---|---|
| 닉네임이 비어 있으면 참가 버튼을 막거나 즉시 안내 | 백엔드가 빈 닉네임을 400으로 거부하는데, 매 왕복 없이 바로 알리는 것이 사용성이 좋음 |
| 참가 성공 시 방 화면으로 전환, 실패(400/409) 시 폼에 머물며 에러 표시 | 이미 구현됨 |
| `playerId`를 `localStorage`에 저장하고 새로고침 시 `GET /api/room`으로 서버에 실제 존재하는지 검증 | 백엔드에 세션/재로그인 개념이 없어 참가할 때마다 새 `Player`가 생성되므로, 클라이언트가 식별자를 직접 보관해야 좌석을 중복 소모하지 않음 |

## 2. 방 상태 화면 → 포커 테이블 (5단계에서 구현)

3단계의 `RoomDebugPanel`은 검증용 임시 화면이며, 5단계부터 실제 포커 테이블로 대체된다.

| 요구사항 | 이유 |
|---|---|
| `players` 배열을 좌석에 매핑해서 표시 | 아래 6번 "확인된 사실" 참고 — 배열 순서가 곧 실제 좌석 순서 |
| 내 플레이어 좌석을 시각적으로 구분 | 여러 명이 보는 화면에서 내 자리를 즉시 인지해야 함 |
| `chips`/`status`(ACTIVE/FOLDED/ALL_IN)/`currentRoundBet` 표시 | FOLDED는 흐리게, ALL_IN은 강조 등 상태별 구분 필요 |

## 3. WebSocket (4단계에서 설계/구현)

| 요구사항 | 이유 |
|---|---|
| `playerId`가 확정된 시점에 `/ws?playerId=`로 연결, 화면 이탈 시 close | 참가자 확정 전에는 연결할 대상이 없음 |
| `STATE` 메시지 수신 시 기존 `ROOM_STATE_RECEIVED` 액션을 그대로 재사용 | 3단계 설계 때 이미 이렇게 재사용하기로 확정 |
| `ERROR` 메시지는 `roomState`를 건드리지 않고 일시적 배너로만 표시 | 내 실수(차례 아님 등)를 알리되 화면 전체 상태는 그대로 유지해야 함 |
| 연결 상태(연결됨/끊김/재연결 중) 배지 표시 | 화면이 안 움직이는 이유(연결 문제 vs 단순 대기)를 구분할 수 있어야 함 |
| 연결이 끊기면 지연 후 자동 재연결 1회 시도, 실패 시 수동 재연결 버튼. 재연결 = 새 WebSocket을 여는 것뿐이며, 연결 즉시 서버가 최신 STATE를 보내주므로 별도 REST 재조회는 불필요 | 백엔드에 세션 복구 기능이 없음(재연결은 새 연결일 뿐) — 이 사실을 그대로 인정하고 설계 |
| 연결 끊김 중에는 액션 UI 전체 비활성화 | 전송이 안 되는 상태에서 액션을 누르게 두면 안 됨 |

## 4. 포커 테이블 UI (5단계)

| 요구사항 | 이유 |
|---|---|
| `players.length` 기준 타원형 좌석 배치, 좌석 인덱스는 `players` 배열 순서 그대로 사용 | 아래 6번 참고 |
| 내 홀카드: `holeCards`가 채워져 있으면 그대로 앞면 표시 | 백엔드가 이미 공개 여부를 판단해서 내려줌 |
| 타인 홀카드: `holeCards`가 빈 배열이면 카드 뒷면 표시 | 위와 동일 — 프론트가 별도로 누구 카드를 가릴지 판단하지 않음 |
| `communityCards` 그대로 표시 | — |
| `pots` 표시(2개 이상이면 메인/사이드 구분 라벨) | 사이드팟이 여러 개일 수 있음 |
| `dealerButtonPosition` 좌석에 버튼 표시, `-1`이면 표시 안 함 | 핸드 시작 전 상태 |
| `currentActorId`와 일치하는 좌석 강조 | 실시간으로 차례를 모두에게 보여야 함 |

## 5. 액션 UI (6단계)

| 요구사항 | 이유 |
|---|---|
| CHECK/CALL/BET/RAISE/FOLD/ALL_IN 버튼, 클릭 시 `{type:"ACTION", action, amount}` 전송 | 확정된 프로토콜 |
| 현재 가능한 액션만 활성화(프론트에서 계산하는 순수 함수) | 백엔드가 "지금 가능한 액션 목록"을 별도로 내려주지 않으므로, `currentActorId`/`currentRoundBet`/`currentBet` 등 기존 필드로 프론트가 직접 판단해야 함. 최종 검증은 여전히 백엔드가 함 |
| 베팅 금액은 +100 버튼을 눌러 증가시키는 방식, "MAX" 버튼으로 즉시 최대치 이동 | 요청된 UX |

**베팅 금액(`amount`)/최소 금액/ALL-IN 관련 세부 규칙은 아래 6번 "백엔드 확인 결과"를 반드시 참고할 것 — 이 표에는 확정된 사실만 반영했고, 확인이 더 필요한 부분은 별도로 표시했다.**

## 6. 백엔드 확인 결과 (구현 전 검토 필요 항목)

`BettingRound.java`, `Room.java`, `ActionMessage.java`를 직접 다시 읽고 확인한 내용이다.

### ✅ 확인됨 (코드로 검증됨)

| 항목 | 사실 | 근거 |
|---|---|---|
| `players` 배열 순서 = 실제 좌석 순서 | 확정 | `Room.addPlayer()`는 리스트 끝에 추가만 하고, 순서를 바꾸거나 제거하는 메서드가 `Room`에 전혀 없다. `GameEngine`의 블라인드/턴 순서 계산(`playerAtOffset`, `activePlayersFrom`)이 전부 이 동일한 `room.getPlayers()` 리스트의 인덱스를 그대로 사용한다. 따라서 `RoomStateResponse.players` 배열의 순서를 프론트가 좌석 순서로 써도 된다. |
| BET/RAISE의 `amount`는 "이번 스트리트에 낼 총액"이지 증가폭이 아님 | 확정 | `applyRaise(Player actor, int newTotal)` — 파라미터명 자체가 `newTotal`이고, `currentBet = newTotal`로 그대로 대입한다. 즉 "300에서 900으로 레이즈"는 `amount=900`을 보내야 하며 `amount=600`(증가분)이 아니다. |
| BET/RAISE 최소 유효 금액 | `currentBet + minimumRaise` 이상이어야 함 | `validateRaise`: `if (newTotal < currentBet + minimumRaise) throw ...` |
| CHECK/CALL/FOLD/ALL_IN은 `amount`를 전혀 사용하지 않음 | 확정 | `BettingRound.applyAction`의 switch 문에서 이 네 액션은 `amount` 파라미터를 참조하지 않음. CALL은 `currentBet - actor.getCurrentRoundBet()`을 서버가 직접 계산, ALL_IN은 `actor.getCurrentRoundBet() + actor.getChips()`를 서버가 직접 계산 |
| "보유 칩 전부를 RAISE로 채워서 보내면" 자동으로 ALL_IN 상태가 됨 | 확정 | `Player.commitChips`가 `chips == 0`이 되면 자동으로 `ALL_IN` 상태 전환. `newTotal`이 정확히 `currentRoundBet + chips`와 같으면 이 경로를 그대로 탄다 |

### ⚠️ 확인 필요 (코드에 검증/방어 로직이 없음 — 프론트 설계 전 결정 필요)

| 항목 | 발견한 사실 | 왜 문제가 될 수 있는지 |
|---|---|---|
| RAISE `amount`가 본인 최대 가능액(`chips + currentRoundBet`)을 초과하는 경우 | `validateRaise`는 `newTotal < currentBet + minimumRaise`만 검사하고, `newTotal`이 플레이어가 실제로 낼 수 있는 금액을 넘는지는 검사하지 않는다. 이 경우 `commitChips`는 보유 칩만큼만 차감하지만, `currentBet`(테이블 전체의 콜 기준액)은 요청한 `newTotal` 그대로 올라간다 | 프론트가 베팅 금액 입력 UI에서 "MAX"를 `chips + currentRoundBet`로 클램프해서 이 상황 자체가 발생하지 않게 막을 수는 있지만, 이건 어디까지나 프론트의 방어일 뿐 백엔드가 막아주는 게 아니다. **이 갭을 백엔드에서 막을지, 프론트 클램핑만으로 충분하다고 볼지 결정이 필요함** (이번 대화에서 백엔드 수정 범위 밖이라 결정만 기록) |

## 7. 게임 진행 표시 (7단계)

| 요구사항 | 이유 |
|---|---|
| `phase` 값을 상단에 표시 | — |
| 새로 추가된 커뮤니티 카드만 등장 애니메이션 재생(이전 렌더의 `communityCards.length`와 비교) | 백엔드는 매번 전체 스냅샷만 보내고 "이번에 몇 장 추가됐는지"는 알려주지 않으므로, 프론트가 직접 비교해서 판단해야 함 |

## 8. 에러/예외 상황

| 상황 | 처리 | 이유 |
|---|---|---|
| 잘못된 액션(ERROR 메시지) | 배너로 표시, `roomState`는 그대로 유지 | 서버가 이미 거부해서 반영 자체가 안 됐으므로 롤백할 필요가 없음 |
| 내 차례가 아닌 경우 | 평소엔 버튼 비활성화로 예방, 그래도 발생하면 서버 ERROR 그대로 표시 | 계산과 서버 판정 사이 짧은 시차 가능성 |
| 연결 끊김 | 액션 UI 전체 비활성화 + 상태 배지 전환 + 재연결 시도 | 전송 자체가 불가능한 상태 |
| 방이 아직 시작되지 않음(`phase === null`) | 테이블 대신 "참가자 대기 중" 화면 + 2명 이상일 때만 "핸드 시작" 버튼 활성화 | 핸드 없는 빈 테이블보다 명확한 대기 상태 표시 |

## 9. 애니메이션/시각적 효과 — 게임 로직과의 분리 (7단계)

**원칙: 애니메이션은 상태를 해석만 하고, 만들거나 지연시키지 않는다.**

- `STATE` 수신 시 `roomState`는 애니메이션 진행 여부와 무관하게 즉시 갱신된다.
- 애니메이션은 렌더링 시점에 "이전 값과 지금 값의 차이"를 감지해서 시각 효과만 얹는다(예: 새로 등장한 카드, 0으로 리셋된 `currentRoundBet`을 보고 칩 이동 효과 재생).
- 애니메이션 재생 여부/속도가 다음 `STATE` 반영을 지연시키지 않는다 — 여러 상태 변경이 연속으로 와도 항상 최신 상태를 기준으로 렌더링한다.

## 10. 반응형 화면

| 요구사항 | 이유 |
|---|---|
| 좌석 배치를 `%`/`vw` 기반 상대 위치로 | 창 크기가 달라져도 테이블 비율 유지 |
| 액션 바 버튼이 좁아지면 줄바꿈 | 창을 줄여도 버튼이 잘리지 않게 |
| 매우 좁은 폭에서는 가로 스크롤 허용 정도로만 대응 | 모바일 최적화는 범위 밖, PC 기준 크기 변화 대응까지만 |

## 11. 접근성/사용성 기본 사항

- 모든 액션 버튼은 네이티브 `<button>` 사용(키보드 조작 가능)
- 턴 강조는 색상 하나에만 의존하지 않고 텍스트 라벨도 병행 (색맹 사용자 고려)
- 에러 메시지 영역에 `aria-live="polite"` 적용
- `prefers-reduced-motion` 감지 시 애니메이션 최소화
- 로딩/비활성 상태는 버튼을 `disabled`로 명확히 표시하고 이유를 텍스트로도 남김
