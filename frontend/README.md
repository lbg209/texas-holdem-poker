# Texas Hold'em Poker Frontend

Spring Boot 백엔드(REST + 순수 WebSocket)와 통신하는 텍사스 홀덤 웹 클라이언트. 서버가 게임 규칙을 전부 판단하고, 프론트는 서버가 내려주는 상태를 그대로 그리는 데만 집중한다 — 낙관적 업데이트나 클라이언트 측 규칙 검증은 없다.

현재는 **단일 고정 테이블 MVP**이며, 이 문서는 실제로 구현된 화면/기능만 기준으로 작성했다.

## 폴더 구조

```
src
├── 🌐 api            # REST 클라이언트 (httpClient, roomApi)
├── 🔌 ws             # WebSocket 훅 (연결/재연결/메시지 송수신)
├── 🗂️ state          # RoomContext — 전역 상태의 유일한 진실의 원천
├── 🃏 types          # 백엔드 DTO와 1:1 대응하는 타입
├── ♟️ game           # 순수 함수 (지금 가능한 액션 계산 등)
├── 🧮 lib            # 순수 유틸 (금액 포맷, 좌석 포지션, 족보 라벨/하이라이트)
└── 🎨 components
    ├── room          # 참가 화면, 게임 규칙 페이지
    └── table         # 포커 테이블 전체 (좌석/카드/칩/액션 UI)
```

## 주요 기능

- **실시간 포커 테이블** — 좌석 배치, 내 좌석 항상 하단 고정, 원근감 있는 크기·간격(3D 변환 없이 CSS만으로), 딜러/블라인드 포지션 배지(BTN/SB/BB/UTG/HJ/CO, 인원 변화에 대응하는 구조)
- **WebSocket 실시간 동기화** — 연결 끊김 자동 재연결(1회) + 수동 재연결, 연결 상태 배지
- **액션 UI** — 체크/콜/폴드/올인 원클릭 버튼, 베팅/레이즈는 칩 프리셋으로 금액을 쌓아가는 빌더. "지금 가능한 액션"은 서버가 알려주지 않으므로 프론트가 직접 계산하되(`game/legalActions.ts`), 최종 검증은 항상 서버가 한다
- **쇼다운 결과 표시** — 족보 이름(로열플러시 별도 판정 포함), 승자 하이라이트, **실제로 승부를 결정한 카드만** 정확히 강조(무관한 킥커는 제외). 하이라이트는 족보 등급에 따라 6단계(하이카드~트리플 gold → 스트레이트/플러시 silver → 풀하우스 orange → 포카드 purple → 스트레이트 플러시 special → 로열 플러시 royal)로 색·광채·펄스 크기가 escalate된다
- **칩 시각화** — 보유 칩을 6단계 등급의 칩 더미 그래픽으로 표현, 핸드 종료 시 손익(+/-) 표시
- **카드/칩 애니메이션** — 딜링(카드 한 장씩 딜인 → 내 카드만 확인), 블라인드/베팅 칩이 팟으로 이동, 커뮤니티 카드 순차 공개(턴/리버는 더 느리게, 긴장감 연출), 쇼다운 시 상대 카드 순서 공개 → 팟이 승자에게 이동
- **홀카드 peek 토글** — 딜링 직후 자동 공개된 뒤로는 클릭할 때마다 뒷면/앞면을 토글(실제 홀덤처럼 확인 후 다시 덮어두기), 쇼다운 시엔 항상 앞면 고정
- **턴 타이머** — 액션 차례인 좌석에 60초 카운트다운 표시(좌석 배지 + 액션바), 10초 이하면 빨간색 강조
- **레디 시스템** — 수동 "핸드 시작" 버튼 대신 레디 토글, 파산하지 않은 전원이 레디하면 자동으로 다음 핸드 시작(첫 핸드는 1초, 이후엔 5초 카운트다운 표시)
- **GAME OVER 오버레이** — 생존자가 1명이 되면 테이블 중앙에 우승자 표시, 더 이상 레디 불가
- **헤즈업 머크 결정 UI** — 2인 쇼다운에서 상대가 자동 공개된 뒤, 내 카드 공개/머크를 8초 안에 선택(테이블 오른쪽 고정 패널, 액션바와 분리해 접근성 확보). 폴드로 이긴 핸드의 승자도 같은 패널에서 카드를 자원 공개할 수 있다
- **게임 규칙 페이지** — 족보 10단계를 카드 예시 + 하이라이트로 직접 보여주며 설명

## 상태 관리 원칙

- **서버 상태가 유일한 진실의 원천**이다. `RoomContext`가 REST 응답과 WebSocket `STATE` 메시지를 모두 같은 리듀서 액션(`ROOM_STATE_RECEIVED`)으로 처리하며, 클라이언트가 미리 결과를 그려두는 낙관적 업데이트는 하지 않는다.
- `playerId`는 `localStorage`에 저장하되 **그대로 신뢰하지 않는다** — 새로고침 시 `GET /api/room`으로 서버에 실제 존재하는지 검증한 뒤에만 참가 상태로 복원하고, 없으면 지우고 참가 화면으로 되돌린다(백엔드에 세션 개념이 없어 직접 관리해야 함).
- WebSocket 연결은 `myPlayerId`가 확정된 시점에만 열고, `onMessage` 콜백의 아이덴티티가 매 렌더 바뀌어도 재연결이 일어나지 않도록 최신 콜백을 ref로 감싸 effect 의존성을 `playerId` 하나로 고정했다.

## 구현 단계

| 단계 | 내용 |
|---|---|
| 1 | Vite + React + TypeScript + Tailwind 스캐폴딩 |
| 2 | 백엔드 CORS 설정 (dev origin만 허용) |
| 3 | REST 연동 — 참가/방 상태 조회/핸드 시작 |
| 4 | WebSocket 연동 — 실시간 상태 동기화, 재연결 |
| 5 | 포커 테이블 UI — 좌석/카드/팟/포지션 배지 |
| 6 | 액션 UI — 체크/콜/벳/레이즈/폴드/올인 |
| 6.5 | 폴리싱 — 쇼다운 결과, 칩 시각화, 규칙 페이지, 다수의 버그 수정 |
| 7 | 카드/칩 애니메이션 — 딜링/블라인드·베팅 칩 이동/커뮤니티 카드 순차 공개/쇼다운 리빌, `roomState`(진짜 최신)/`displayState`(연출 지연) 분리 아키텍처 |
| 8 | 게임플레이 완성도 — 턴 타이머+자동 폴드, 레디 시스템+자동 시작, GAME OVER 감지, 폴드승 카드 공개, 헤즈업 머크 결정, 홀카드 peek 토글, 족보 등급별 하이라이트 |

각 단계가 "세션 하나"에 대응하던 초반과 달리, 7단계 이후로는 애니메이션 뼈대가 갖춰진 뒤 짧은 주기로 기능 하나씩(설계→구현→테스트) 추가하는 방식으로 진행돼서 8단계는 여러 기능을 한데 묶었다 — 세부 내역은 위 "주요 기능"과 커밋 히스토리 참고.

## 기술적으로 흥미로웠던 부분

- **원근감을 3D 변환 없이 구현**: 테이블을 실제로 기울이는 CSS 3D(`perspective`+`rotateX`)도 시도해봤지만, 텍스트/카드가 같이 기울어져 가독성이 떨어지는 문제가 있었다. 대신 좌석 좌표 계산(`computeSeatPositions`)에서 나(하단)에 가까운 좌석은 넓게·크게, 먼 좌석은 좁게·작게 배치하는 "가짜 원근감"으로 정리했다 — 앉아서 보는 느낌은 유지하면서 텍스트는 항상 수평.
- **쇼다운 하이라이트의 "의미 있는 카드만" 판정**: 서버가 내려주는 `bestFive`를 그대로 다 하이라이트하면 원페어처럼 킥커가 섞인 족보에서 승부와 무관한 카드까지 강조되는 문제가 있었다. 족보별로 실제 조합을 구성하는 카드만(원페어=페어+최상위 킥커 1장, 트리플/포카드=조합 카드만, 스트레이트/플러시/풀하우스=5장 전부) 골라내는 로직(`getHighlightedCardsForShowdown`)으로 해결했다 — 이 로직은 동시에 족보 등급별 하이라이트 색상(`getHighlightColorForHandRank`)도 함께 반환해서, 카드 색·텍스트 스타일이 같은 곳에서 일관되게 결정된다.
- **REST/WebSocket 이원화가 만든 버그들**: "핸드 시작" REST 응답이 요청자를 모른 채(관전자 시점) 만들어져서 클릭한 사람 화면에서 순간적으로 본인 카드가 사라지던 문제, 폴드로 핸드가 조기 종료됐을 때 이미 끝난 베팅 라운드의 잔여 상태(`currentActorId`)가 응답에 남아 상대방 화면에 "아직 내 차례"처럼 보이던 문제 — 둘 다 REST와 WebSocket이 같은 게임 상태를 서로 다른 시점에 반영하면서 생긴 문제였고, 백엔드 응답을 개인화하거나 상태를 명시적으로 정리하는 방식으로 고쳤다.
- **`roomState`/`displayState` 분리와 그로 인한 버그들**: 애니메이션 큐 도입 후, 서버의 "진짜 최신 상태"(`roomState`)와 "화면에 지금 그려지는 상태"(`displayState`)가 몇백 ms~몇 초씩 어긋나는 구간이 생겼다. 이 구간에 액션 버튼이 옛 스트리트 기준으로 계속 활성화돼 있거나(스트리트 전환 애니메이션 중 `currentActorId`/`currentBet`을 얼려두지 않았던 버그), 액션과 무관한 상태 갱신(레디 토글)만으로 "방금 체크했다"는 라벨이 잘못 붙는 버그가 있었다 — 둘 다 "무엇을 근거로 액션이 실제로 일어났다고 판단할지"를 더 엄격하게(단순 `currentActorId` 비교가 아니라 `phase` 변화까지) 고쳐서 해결했다.
- **React StrictMode의 개발 모드 이중 실행이 만든 버그**: 홀카드 peek 토글에서 "이미 처리한 카드인지" 상태를 `ref`로 직접 추적했더니, StrictMode가 effect를 mount→cleanup→mount로 두 번 실행하면서 첫 실행이 ref를 먼저 갱신해버려 두 번째 실행이 "이미 처리됨"으로 오판, 타이머 예약 자체를 건너뛰어 기능이 아예 동작하지 않았다. `ref` 기반 수동 추적 대신 React가 권장하는 "prop이 바뀌면 `key`로 컴포넌트를 통째로 리마운트" 패턴으로 바꿔서 해결했다.

## 아직 구현하지 않은 것 (의도적으로 미룸)

- **방 나가기(퇴장) 기능**: 탭을 닫아도 서버에는 좌석이 영구히 남는다.
- **닉네임 중복 방지**: 같은 방에 같은 닉네임으로 여러 명이 들어올 수 있다.
- **사운드 효과**: 카드 딜/뒤집기/칩 이동에 대응하는 소리가 아직 없다.
- **핸드 히스토리**: 지난 핸드 결과를 다시 볼 방법이 없다.
- **3명 이상 쇼다운의 순서대로 머크**: 지금은 정확히 2명이 겨루는 헤즈업 쇼다운만 머크를 지원한다.
- **방 생성/멀티룸/회원가입**: 지금은 서버 전체에 고정된 단일 방 하나뿐이고, 로그인/게스트 계정 개념이 없다.
- **캐시게임 리바이 / 매치 재시작**: GAME OVER 이후엔 그냥 멈춘다.

## Claude Code와 함께 개발

이 프론트엔드도 백엔드와 마찬가지로 [Claude Code](https://claude.com/claude-code)와 페어 프로그래밍 방식으로 개발했다. 매 기능마다 설계안을 먼저 제시받아 검토·승인한 뒤 구현하고, 구현 후에는 빌드/린트 결과를 확인하는 과정을 반복했다 — 커밋 히스토리에 그 단위(기능 하나 = 커밋 하나)가 그대로 남아 있다.
